# BLLM-002: Model selection and weight loading

**Status:** draft
**Change class:** architectural

## Intent

- **What is changing:** The harness gains a target model and the CPU-side code
  to load it. GGUF container parsing, metadata and tensor-index extraction,
  Q4_0 block layout, a CPU reference dequantizer, and the tokenizer. Weights
  are fetched from a CDN, verified by SHA-256, and cached in OPFS.

  **No GPU work.** Nothing in this packet dispatches a shader. Every line is
  platform-neutral C++ and natively testable, which is why it comes before the
  kernels rather than alongside them.

- **Why the change is necessary:** Every kernel decision downstream — buffer
  packing, dequant shader shape, attention layout — is determined by the
  model's architecture and quantization format. Choosing them while writing
  kernels would mean rewriting kernels. This packet also closes the standing
  gap that the repo's automated tests cover only arithmetic and ownership:
  GGUF parsing and dequantization are substantial logic with a deterministic
  reference, so they are testable in CI with no GPU and no browser.

- **Expected behavior changes:** The page gains a load phase: fetch with
  progress, SHA-256 verification, OPFS cache, then a parsed model summary
  (architecture, layer count, tensor count, quantization) rendered from the
  actual file. Still no inference and no token generated.

- **Guaranteed invariants/contracts:**
  - The GGUF parser treats the file as **untrusted input**. Every offset and
    length is bounds-checked against the actual buffer before use; a malformed
    file produces a named error, never a read outside the mapping (SL.con.3).
  - Parsing is a pure function of bytes. No I/O, no GPU, no globals — so it is
    exhaustively testable from fixtures.
  - The whole model is never resident in the WASM heap. Parsing reads the
    header and index; tensor data is consumed in chunks.
  - A SHA-256 mismatch fails the load loudly. The page never runs against
    weights it cannot identify.

## The decision

**Model: Qwen3-0.6B. Quantization: Q4_0. Container: GGUF. Targets: Chrome and
Edge desktop.**

Verified from `config.json`, not assumed:

| | |
|---|---|
| `hidden_size` | 1024 |
| `intermediate_size` | 3072 |
| `num_hidden_layers` | 28 |
| `num_attention_heads` / `num_key_value_heads` | 16 / 8 — GQA, 2:1 |
| `head_dim` | **128** |
| `vocab_size` | 151,936 |
| `rope_theta` | 1,000,000 |
| `rms_norm_eps` | 1e-6 |
| `tie_word_embeddings` | true |
| `hidden_act` | silu (SwiGLU) |

**`head_dim` is explicit and is not `hidden_size / num_attention_heads`.**
16 × 128 = 2048 while hidden is 1024, so `q_proj` is [1024 → 2048] and
`o_proj` is [2048 → 1024]. An implementation that derives head_dim from the
hidden size will produce silently wrong shapes. This is the single most
likely place to get the model wrong.

Embeddings are 151,936 × 1024 ≈ 155.6M parameters — about 26% of the model —
and are tied, so the same table serves the output projection.

**Why this model.** Selection was on *kernel surface*, not benchmark quality:
the harness is the demonstration. Qwen3 needs dequant, RMSNorm, RoPE, GQA
attention, SwiGLU, output projection, and QK-norm — the standard decoder set
plus one trivial addition. Rejected: Gemma 4 E2B, whose checkpoint is 10.25 GB
despite the "2B effective" name and which carries vision and audio towers we
would never call; and `gemma-4-26B-A4B`, because MoE optimizes compute while
the browser's binding constraint is resident bytes — 26B parameters must be
resident to route 3.8B of work. Llama-3.2-1B was the runner-up: one fewer
kernel, ~280 MB more download.

Every kernel written here transfers unchanged to Qwen3-1.7B or Llama-3.2-1B.

**Limits floor: none declared beyond the WebGPU defaults.** The harness asks
for the adapter's advertised maxima and plans residency from what is *granted*,
which varies per device and is known only after acquisition. Declaring a floor
above the defaults would trade portability for uniformity we do not need yet.
Weight packing must therefore work at the 128 MiB spec-default storage-binding
limit and use more when granted.

## Acceptance Criteria

- [ ] A GGUF file parses to a tensor index and metadata map, verified against
      fixtures generated by `tools/make_fixture_gguf.py`.
- [ ] Malformed inputs fail with named errors, never a bounds violation:
      truncated header, tensor offset past EOF, length overflowing the file,
      bad magic, unknown version, and a declared tensor count that cannot fit.
- [ ] Q4_0 dequantization matches a reference computed independently of the
      implementation, to exact bit equality on a fixture block.
- [ ] The tokenizer round-trips a fixture corpus: `decode(encode(s)) == s`.
- [ ] Model config read from the file matches the table above, `head_dim`
      explicitly asserted as 128 rather than derived.
- [ ] Parsing a 420 MB file never holds more than a stated bound in the WASM
      heap, asserted by instrumentation rather than by inspection.
- [ ] SHA-256 mismatch aborts the load with a distinct, user-visible error.
- [ ] The page reports architecture, layer count, tensor count and quantization
      read from the actual downloaded file.
- [ ] All of the above pass natively in CI, with no GPU and no browser.

## Verification Plan

| Test | What it pins |
|---|---|
| `gguf_parse_test` | Header, metadata KV types, tensor index. Fixtures committed, generated by a script so they can be regenerated and diffed. |
| `gguf_malformed_test` | Each malformed case above produces its named error and reads nothing out of bounds. This is the test that matters: the file arrives from a CDN. |
| `quant_q4_0_test` | Block layout and dequantization against independently computed values, bit-exact. |
| `tokenizer_test` | Round-trip over a fixture corpus, including multi-byte UTF-8 and the special tokens. |
| `model_config_test` | Parsed config equals the known-good table, `head_dim` asserted explicitly. |

Fixtures are small synthetic GGUFs, not the real model — CI must not download
420 MB. The real file is exercised once, manually, and its SHA-256 recorded.

## C++ Architecture Note

- **Core components touched:** New, all under `src/core/`: `gguf/` (reader,
  types), `quant/` (Q4_0 block layout, reference dequant), `tokenizer/`,
  `model/` (config derived from GGUF metadata).

- **Platform wrappers touched:** `src/wasm/bindings.cpp` gains a load entry
  point and a summary reporter. `web/` gains fetch-with-progress, SHA-256
  verification and the OPFS cache — all in JS, because the browser provides
  both primitives and reimplementing them in C++ would be gratuitous.

- **Public interfaces changed:** None existing. Introduced: `gguf::Reader`,
  `gguf::TensorIndex`, `quant::Q4_0Block`, `quant::dequantize_reference`,
  `tokenizer::Tokenizer`, `model::Config`.

- **New files/classes/targets/modules:** Sources added to `browser_llm_core`
  in **both** configurations — unlike `device.cpp`, none of this needs
  `webgpu.h`, so native source parity holds here and CI compiles and tests
  every line.

- **Dependency edges added or removed:** None outward. No third-party
  dependency: GGUF is simple enough to parse directly, and vendoring an
  existing loader would defeat the premise.

- **Ownership/lifetime model:** The parser borrows a `std::span<const
  std::byte>` and owns nothing; the caller owns the bytes. The tensor index
  holds offsets and lengths, not pointers, so it cannot outlive its buffer
  into undefined behavior. Exceptions are off, so errors are returned as
  values, following the pattern `dispatch_count` already sets (E.25).

- **Test surface independent of UI wrappers:** All of it. Every component here
  is a pure function of bytes and runs in the native test binary.

- **Why this decomposition is appropriate:** Splitting the model decision and
  the CPU-side loader from the GPU kernels means the entire first half is
  natively testable, and the kernels arrive with their inputs already proven.
  The alternative — writing the loader and kernels together — would put the
  first genuinely complex logic in the repo behind a GPU that CI cannot reach.

- **What is intentionally not abstracted:** No tensor library, no graph
  abstraction, no backend interface. There is one model and one quantization
  format; an abstraction over a single implementation would be ornament.
  `quant/` handles Q4_0 only, and gains formats when a second is needed.

## C++ Performance Note

- **Target hardware/workload:** Chrome and Edge desktop. Workload for this
  packet is model load only: fetch, verify, parse, cache. Not inference.

- **Performance budget:** Model load is performance-sensitive by this repo's
  default. Parsing the header and tensor index is an index operation over
  metadata, not over 420 MB, and should complete in **under 100 ms** on the
  blessed target. SHA-256 over 420 MB is bounded by the browser's WebCrypto
  and is measured, not budgeted, in this packet.

- **Baseline measurement:** None exists; this packet establishes it. Recorded
  measurements must name the device, the browser build, and whether the file
  came from network or OPFS — cold and warm load differ by the entire download.

- **Hot paths touched:** None yet. Dequantization here is the **reference**
  implementation, whose purpose is being obviously correct so it can serve as
  the oracle for the GPU kernel. It is explicitly not optimized, and must not
  be: a clever reference that is wrong in the same way as the kernel proves
  nothing.

- **Allocation/copy/serialization behavior:** The binding constraint. A 420 MB
  model must not be resident in the WASM heap — wasm32's address space makes it
  wasteful now and impossible as models grow. Tensor data is consumed in
  chunks, and the peak heap held during load is asserted by a test rather than
  assumed.

- **Concurrency model:** Single-threaded, unchanged. Fetch and hashing are the
  browser's, off the critical path in the worker.

- **Edge AI runtime/backend/configuration:** None. No inference runtime exists
  and none will be adopted.

- **Before/after measurement plan:** No "after" — nothing is being optimized.
  The measurements taken here become the baseline that BLLM-003's kernels are
  compared against.

- **Accuracy/product-contract risk from performance optimizations:** None; no
  optimization is performed. The accuracy risk that does exist is Q4_0
  dequantization correctness, which is why it is pinned bit-exactly against an
  independent reference rather than by tolerance.

## Records

- Guidelines consulted before design, per `workflow.md`: `cpp-guidelines`
  searched for untrusted-binary parsing and bounds safety — SL.con.3 (avoid
  bounds errors), SL.4 (type-safe standard library use), P.11 (encapsulate
  messy constructs) shaped the span-based, offsets-not-pointers parser
  contract. E.25 (simulate RAII without exceptions) governs the error-return
  style, consistent with `dispatch_math`.
- Model sizes were measured from the Hugging Face API, not estimated:
  Qwen3-0.6B 1.50 GB, Llama-3.2-1B 2.47 GB, Qwen3-1.7B 4.06 GB,
  gemma-4-E2B 10.25 GB (bf16 checkpoints).
- BLLM-003 follows: native Dawn plus the first GPU kernels, using this
  packet's reference dequantizer as the correctness oracle.
